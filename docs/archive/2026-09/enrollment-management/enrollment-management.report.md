### 1.2 결과 요약

`enrollment`/`waitlist` 가 **엔티티 + 빈 Repository** 뿐이던 상태에서 **전 계층 완결**로
올라갔다. API 9개가 개통됐고 `openapi3.json` 이 path 8→16 / operation 10→19 로 늘었다.

**이 사이클의 핵심 난제는 하나였다** — 마지막 한 자리에 여러 명이 동시에 신청할 때 정확히
한 명만 성공하는가. 실측으로 답했다: 100건 동시 요청 → 1건 성공 · 99건 정원 초과 거부,
3회 반복에도 편차 0.24초로 안정적.

### 1.3 전달된 가치

| 관점 | 내용 |
|------|------|
| **Problem** | 강의는 등록·공개까지 완결됐으나 **아무도 신청할 수 없었다.** `klass.enrollment_count` 는 읽는 코드만 있고 쓰는 코드가 없어 **항상 0** 이었고, 그래서 `ck_klass_count` 도 도달 불가였다 — 정원 관리가 선언만 되고 작동하지 않았다 |
| **Solution** | ERD 정본 §4 의 동시성 규약을 그대로 구현했다. 모든 좌석 트랜잭션이 `klass` 행을 `SELECT ... FOR UPDATE` 로 **가장 먼저** 잡아 경합을 한 행에서 직렬화하고, 검사·INSERT·카운터 갱신을 한 트랜잭션으로 끝낸다. 좌석 유스케이스를 **단일 서비스**에 모아 트랜잭션 경계와 코드 구조를 일치시켰다 (D-29) |
| **Function/UX 효과** | API 9개 개통. 정원이 차면 거부되고, 사용자가 원할 때만 대기열에 들어가며, 앞자리가 비면 **신규 신청자보다 먼저** 승격된다(순변화 0). 개설자는 자기 강의에 신청할 수 없다(3지점 차단). 취소는 **결제일 기준 기간 + 강의 종료일** 두 관문을 통과해야 한다 |
| **Core Value** | **"마지막 한 자리에 100명이 동시에 신청해도 정확히 1명만 성공한다"** 를 락과 DB 제약으로 이중 보증했다. 카운터가 실제 좌석 점유 행 수와 어긋나지 않음을 정합성 쿼리 5종으로 증명한다 |

### 4.2 R-01 — 만료 회수 부재의 실제 영향

**이 사이클이 남긴 가장 큰 부채다.** 완화가 아니라 관측만 확보했다.

```
정원 10 강의에서 10명이 신청하고 아무도 결제하지 않으면
→ 그 강의는 영구히 만석이 된다
→ 사용자가 스스로 취소하지 않는 한 회수 경로가 전무하다
```

| 준비된 것 | 상태 |
|-----------|------|
| `expires_at` 이 정확히 채워진다 | ✅ 출처별 30분/10분 |
| 만료된 `PENDING` 은 결제가 거부된다 | ✅ `Enrollment.confirm` — **유일한 만료 방어선** |
| 회수 시 좌석 반납 + 승격 로직 | ✅ 취소 경로에 이미 있다 (재사용 가능) |
| 만료 좌석 관측 쿼리 | ✅ `EnrollmentFlowIntegrationTest` 정합성 절 |
| **회수 트리거** | ❌ **없다** |

외부 배치 서버가 붙으면 **즉시 동작한다** — 남은 것은 트리거뿐이다.

## 6. 회고

### 6.1 잘된 것 (Keep)

**① 스파이크가 module-2 를 통째로 되돌릴 뻔한 것을 막았다.**
설계가 주장만 하던 5건(`@Lock` 파생 쿼리 · H2 의 `FOR UPDATE` + LIMIT · `record` 프로퍼티
바인딩 등)을 구현 전에 실측했다. 13건 전부 통과했지만, 그 과정에서 **실측이 아니었으면
몰랐을 4가지**가 나왔다 — 특히 "프로퍼티 블록이 없으면 중첩 `record` 가 예외가 아니라
`null` 이라 **기동은 성공하고 첫 신청에서 NPE**" 는 기동 테스트로는 절대 안 잡힌다.
project-setup 의 선례(`STORED` 거부 발견)를 따른 것이 값을 했다.

**② 게이트를 앞에 둔 모듈 순서.**
`module-0`(스키마 동작 검증)을 첫 모듈로 두어, `waitlist` 제약이 정말 거부하는지를
구현 전에 확인했다. 여기서 "제약이 **존재한다**"와 "제약이 **작동한다**"가 다르다는 것을
발견해 설계를 정정했다 — 이 저장소의 기존 전제("선언했다 ≠ 생성됐다")를 한 단계 더 밀었다.

**③ 시각을 조작하지 않고 시간 조건을 만든 것.**
`Clock` 이 `systemDefaultZone()` 이라 테스트에서 시간을 옮길 수 없었는데, 데이터로 풀었다
— 취소 기간 0일이면 확정 직후가 이미 초과이고, 종료일이 과거인 강의는 그 자체로 끝난
강의다. 시계 조작보다 실제 사용자 경험에 가깝고 시스템 시각에 흔들리지 않는다.

**④ 근거를 코드에 남긴 것이 Check 에서 회수됐다.**
`cancel()` 이 `isCancellableAt` 을 재사용하지 않는 이유를 javadoc 에 적어 뒀더니,
gap-detector 가 "설계와 다르다"를 지적했을 때 **어느 쪽이 옳은지 즉시 판정**할 수 있었다.
근거가 없었으면 코드를 버그로 오해하고 고쳤을 것이다.

### 6.2 개선할 것 (Problem)

**① "문서 일부만 갱신"을 또 반복했다.**
klass-management 회고가 이미 지적한 항목인데, 분석 문서 §8 에 조치 결과를 쓰면서
§2.6·§2.7·SC-3 의 수치를 그대로 뒀다. **같은 문서가 "31/31 해소"와 "30/31 부재"를 동시에
말하는 상태**를 만들었다. 별도 커밋으로 정정했지만 재발이다.

> **원인**: 문서를 "덧붙이는" 방식으로 갱신하면서, 이미 있던 수치가 그 변경의 영향을
> 받는지 훑지 않았다. **수치를 바꿀 때는 그 수치가 나오는 모든 자리를 grep 해야 한다.**

**② Check 에서 "문서를 코드에 맞춘다"로 끝낸 것이 얕았다.**
D-43(패키지 양방향)을 문서 정정만으로 처리했는데, 사용자가 "헥사고날에 문제 없나"라고
물어 다시 보니 **절반은 실제로 없앨 수 있었다.** `waitlist` 가 쓰지도 않는 `status` 필드
때문에 `enrollment` 를 경유하고 있었고, 이는 klass-management D-24 가 이미 고친 것과 같은
모순이었다.

> **원인**: 갭을 발견했을 때 "문서가 틀렸나 코드가 틀렸나"만 물었고, **"둘 다 고칠 수 있나"**
> 를 묻지 않았다. 코드 쪽 개선 여지를 한 번 더 확인했어야 했다.

**③ RestDocs 토큰 함정에 6건을 한꺼번에 날렸다.**
`restdocs-api-spec` 이 Bearer 토큰의 payload 를 base64 JSON 으로 파싱한다는 것을 몰라
임의 문자열을 넣었다가 6건이 동시에 실패했다. 에러 메시지가 "0xfffd 문자"라 **인코딩
문제로 착각**할 모양이었다.

> **원인**: 기존 컨트롤러 테스트 3개가 모두 같은 토큰 값을 쓰는 것을 **패턴으로 보지 않고
> 우연으로 넘겼다.** 세 파일이 같은 상수를 쓰면 이유가 있다.
